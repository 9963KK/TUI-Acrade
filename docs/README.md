## 设计来源

以下记录来自 2026-09-24 的本任务讨论，是文档的需求来源；编号用于追溯。

| 编号 | 用户要求或方向 |
| --- | --- |
| U-01 | 项目作为社区共创项目，需要模块划分和功能解耦。 |
| U-02 | 每个游戏有独立存档，存档接入需要明确规范。 |
| U-03 | 游戏开发需要准则，二创引用需要说明，技术改进可以提交 PR。 |
| U-04 | 后续方向调整为游戏独立存在，平台提供基础入口，接入游戏必须能够在 TUI 上运行。 |
| U-05 | 用户通过 GitHub 加载项目游戏目录，在选择界面安装部分游戏。 |
| U-06 | 本地最多安装 12 个游戏，需要安装、删除、重新安装和替换管理。 |
| U-07 | 先沉淀并规范化设计文档，再进行后续实现。 |
| U-08 | 系统都需要支持，最终通过终端命令打开平台；本轮明确 Windows、macOS、Linux 为支持目标。 |
| U-09 | 现阶段游戏是否联网取决于游戏自身设计，不限制为离线游戏。 |
| U-10 | 游戏分发选择 A：提供预构建可运行包，平台自动选择对应系统资产，玩家无需安装语言环境或本地编译。 |
| U-11 | 平台自身采用一条安装命令，自动下载并配置启动入口，同时保留手动下载安装方式。 |
| U-12 | 当前暂时只做本地，GitHub 仓库与对外发布后续再定。 |
| U-13 | 平台原创代码采用 MIT 许可证，游戏与第三方素材仍遵守其适用许可证。 |
| U-14 | 存档与否由游戏本身决定，平台不强制每个游戏提供存档。 |
| U-15 | 首版支持 Windows x86_64、Linux x86_64、macOS Intel 与 Apple Silicon，共 4 种组合。 |
| U-16 | 平台技术栈采用 0.7 评审建议：Go + Bubble Tea。 |
| U-17 | 通过 `tplay` 命令启动整个项目。 |
| U-18 | 玩家是使用命令行的程序员，自己用 git 获取仓库；游戏来自平台仓库内置目录、独立 git 仓库或本地目录。平台不负责分发，核心是接入的游戏能正确启动。 |
| U-19 | 游戏出现在游戏厅的前提：通过检查、运行环境已安装、用户确认安装。内置游戏也需确认安装，首次使用时以列表供用户选择。 |
| U-20 | 游戏厅需要启动界面，选项为进入游戏厅、安装游戏、退出游戏厅；界面简洁，选中项整行反色。 |
| U-21 | 安装后检查未通过的游戏在游戏厅中显示为需要修复，方便玩家自行排查。 |
| U-22 | 不设安装数量上限，游戏厅提供搜索。 |
| U-23 | 内置游戏可以卸载：删除运行环境并从游戏厅移除，源码保留在仓库中。 |

U-04 调整了早期“游戏统一使用平台画布和进程内接口”的方案。目标架构以独立游戏进程为准，不再强制统一游戏语言、渲染框架或游戏内部 API。

U-02 经 U-14 进一步明确为：是否提供存档由游戏决定；需要持久数据的游戏拥有独立数据和存档逻辑。平台提供专属数据目录，不强制存档或统一数据结构。统一存档 SDK、远程存档服务和平台备份策略保留为未来可选能力。

## 文档约定

- **已确认方向**：直接来自上述用户要求。
- **默认方案**：为落地所提出的架构选择，作为实现评审基线，可通过设计变更调整。
- **待决事项**：尚未确定，不能当成已实现或已获用户确认的事实。
- **必须 / 不得**：在对应草案被采用后需要满足的契约。
- **应 / 建议**：推荐默认值；偏离时应在 PR 中解释原因。
- 示例 ID、版本、人数和安装包地址只用于说明，不代表实际发布内容。
- 规范正文使用仓库约定的 `<spec-entry>` 闭合标签，并记录类别、关键词、日期和来源。

### 本轮确认记录

- D-01（U-08、U-15）：首版正式支持 Windows x86_64、Linux x86_64、macOS x86_64 / arm64，不能默认把 Windows 推迟到后续版本；最低系统版本另行验证。
- D-02（U-08、U-17）：玩家通过终端命令启动大厅，命令名为 `tplay`。命令入口与安装方式是不同决策。
- D-03（U-09）：不以离线运行作为首版游戏收录门槛。联网能力和联网失败的游戏内反馈由游戏负责，平台负责需求展示。
- D-04（U-10）：游戏采用预构建可运行包分发；语言运行环境由包提供，原生程序按实际依赖打包。平台自动选择兼容资产，安装阶段不让玩家准备语言环境或编译源码。开发者从源码开发的方式不受该分发决策限制。
- D-05（U-11）：平台自身提供一条安装命令，自动下载并配置终端启动入口，同时保留手动下载安装。不同系统可以使用不同安装命令；启动命令为 `tplay`，升级策略尚未确定。
- D-06（U-12）：当前先做本地开发和验证，暂缓 GitHub 仓库配置及发布。远端目录仍保留为目标架构；本地阶段不虚构仓库地址或发布资产。
- D-07（U-13）：平台原创代码采用 MIT，见 [LICENSE](../LICENSE)。游戏与第三方材料分别保留适用授权，不能因为平台采用 MIT 而自动重新授权。
- D-08（U-14）：存档能力由游戏设计决定，无存档游戏允许接入。需要写持久数据时才应用数据目录和存档可靠性约定；没有确认自动备份或固定保留份数。
- D-09（U-16）：平台使用 Go + Bubble Tea 实现，以单文件可执行程序构建。Python 平台代码已移除，Python 游戏可继续使用 `kit/arcade_kit`。
- D-10（U-18 至 U-23）：安装模型改为“获取（内置 / git / 本地目录）→ 确认 → 准备运行环境 → 检查与试运行 → 登记”，详见[游戏安装规范](game-installation.md)。U-05、U-06、U-10、U-11 与[游戏安装管理规范](game-management.md)因此不再适用；原记录保留以便追溯。

</spec-entry>

### 工程默认方案

Q-08 使用分层版本：平台及游戏发布版本采用 SemVer，目录与接入清单使用独立整数协议版本，存档版本由游戏自行定义。首版明确支持版本 `1`；不识别的行为契约拒绝执行。此项由设计整理阶段提出作为工程基线，未记为用户逐项确认，具体规则见[游戏接入规范](game-integration.md)。

## 当前交付边界

设计任务交付了规范文档和平台 MIT 许可证。随后的 M1 实现已把坦克大战拆为独立游戏（`games/tank/`），平台（`platform/`，Go）按本规范的清单协议 1 读取游戏、注入 `TUI_ARCADE_*` 环境变量并交接终端，Python 共用绘制代码拆为可选工具包 `kit/arcade_kit/`，另提供只用标准库的最小样例 `templates/minimal-game/`。尚未生成正式 JSON Schema、配置远程仓库、发布安装包或实现安装管理。当前运行方式以项目根目录 README 为准。

0.7 的技术评审补充了实现层面的建议，分别写入各规范并以“（0.7）”标注：平台技术栈（Q-09）、Windows 终端交接机制、ID 保留名、能力枚举、各系统目录、单一事实来源的安装记录、包格式与解包、GitHub 固定下载地址。

后续实现顺序与验收条件见各规范，不应仅凭目录草图批量移动现有代码。
