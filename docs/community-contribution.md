# 社区贡献规范

| 项目 | 内容 |
| --- | --- |
| 版本 / 状态 | 0.6 / 贡献规范草案，平台 MIT 已确认，当前先本地开发；0.7 评审补充起步样例 |
| 来源 | U-01、U-03、U-04、U-10、U-12、U-13；具体发布与评审流程为默认方案 |
| 适用范围 | 新游戏、关卡、平台能力、修复、文档、翻译与测试 |

## 1. 贡献边界

游戏可以使用不同语言和 TUI 技术，但必须满足[游戏接入规范](game-integration.md)。平台只统一清单、包管理、启动和数据目录边界。

新增玩法优先放在对应游戏中。只有多个游戏或平台本身确实需要的能力，才考虑进入公共模块；不因为单个游戏的内部实现而扩大平台接口。

社区贡献可以包括关卡设计、可访问性改进、翻译、测试和文档，不局限于游戏源码。

（0.7）新游戏可从 `templates/minimal-game/` 复制起步：它只用标准库，演示清单、数据目录与退出码。开发期间用 `TUI_ARCADE_DEV_GAMES=<包含游戏文件夹的目录> python3 -m arcade` 在大厅中调试。Python 游戏可选用 `kit/arcade_kit/`，选用时须在构建安装包时一并打入，不能依赖平台运行时提供。

## 2. 每个游戏需要提供的材料

| 材料 | 最低内容 |
| --- | --- |
| `game.json` | 稳定 ID、版本、入口、兼容条件、文档和数据约定 |
| `README.md` | 玩法、操作、退出方式、独立运行步骤、支持平台和已知限制 |
| `LICENSE` | 适用于本游戏的许可证文本及必要声明 |
| `CREDITS.md` | 原创说明，或第三方代码、关卡、图片、字体、音效等来源 |
| 构建与依赖说明 | 如何从源码产生可安装资产，依赖版本与运行时要求 |
| 测试 | 核心规则、接入行为；有存档时覆盖保存、读取、异常及迁移 |
| 维护信息 | 维护者、问题反馈入口和适用版本 |

不要求所有游戏具备关卡或存档，但不得声明实际没有实现的能力。

## 3. 二创与第三方引用

每项复用材料记录以下信息：

| 字段 | 示例含义 |
| --- | --- |
| 上游来源 | 项目仓库或材料的原始发布地址 |
| 来源版本 | tag、commit 或有明确日期的版本 |
| 复用范围 | 具体模块、文件、关卡或素材 |
| 作者与授权 | 作者、许可证文本位置、需要保留的声明 |
| 本项目改动 | 格式转换、规则移植、终端适配或其他修改 |

代码、地图和音画素材分别核对授权，不能仅依据仓库首页写有 MIT 就把所有第三方资源视为同一许可证。未明确取得所需授权的材料不进入官方发布包。

平台原创代码已选择 MIT，许可证文本见根目录 [LICENSE](../LICENSE)。游戏及第三方代码、关卡和素材仍分别适用其授权；平台采用 MIT 不会自动改变这些材料的许可证。本次决策不代表已批准复用此前搜索到的全部素材。

MIT 声明采用社区项目署名 `TUI Arcade contributors`；贡献者保留其应有版权，具体上游声明随对应材料保留。来源审核和授权兼容性检查仍需在对外发行前完成。

## 4. PR 分类与要求

| PR 类型 | 需要说明 |
| --- | --- |
| 新游戏 | 玩法、独立运行方式、兼容平台、引用、接入测试与安装包生成方式 |
| 游戏修改 | 行为变化、影响范围、测试；是否改变存档格式 |
| 新关卡 / 素材 | 来源、格式、加载校验和游戏内验证 |
| 平台修复 | 可复现问题、修改后的行为和回归验证 |
| 公共协议变更 | 动机、兼容策略、受影响游戏、迁移方案和样例验证 |
| 渲染或运行技术替换 | 具体收益、兼容终端、性能或稳定性证据、回退路径 |

小范围内部修复无需设计提案；涉及公共接口、发行机制、存档边界或系统支持变化的改动，应先更新对应设计文档并评审。

提交只包含该 PR 的文件，不顺手重写其他游戏或平台无关模块。

## 5. 测试分层

- **游戏测试**：核心规则、边界条件、错误处理；尽量在无需真实终端时运行。
- **接入测试**：独立启动、清单校验、数据目录和生命周期，对应 GI 验收编号。
- **平台测试**：目录、安装记录、名额、失败恢复，对应 GM 验收编号。
- **真实终端验证**：启动、输入、尺寸变化、中断和恢复，不能完全由模拟屏幕替代。
- **存档迁移验证**：用实际旧版本样本验证，记录不兼容情况，不能只用新版本生成的数据自测。

遵循项目代码质量基线：公共接口、边界和失败路径应有测试；新增核心模块以 80% 以上覆盖率为目标，但覆盖数字不能替代行为验证。外部网络依赖在自动测试中使用替身，另行做真实发布资产的集成验证。

## 6. 官方发布流程

当前先本地开发，GitHub 仓库和对外发布暂缓。以下是后续开启公开发行时的流程；本地阶段可以先验证包构建和安装行为。

```text
贡献 PR
  → 代码、来源与协议评审
  → 自动测试和真实终端验证
  → 为声明的平台构建游戏包
  → 核对清单、入口、版本、授权文件和校验值
  → 发布固定版本资产
  → 更新官方目录
  → 验证玩家安装、启动与卸载路径
```

目录维护者负责游戏 ID 的唯一性及发布条目的有效性。游戏维护者负责内部实现、依赖、兼容和迁移。未准备完安装资产的开发中游戏不加入“可安装”目录。

已确认使用预构建包分发。贡献者或项目发布流水线必须为声明支持的系统和架构生成可运行资产，随包提供所需语言运行环境。玩家安装路径不得要求安装 Python、Node 等语言环境或编译源码；构建工具与源码开发方式由各游戏自行选择。发布验证需要覆盖没有额外语言环境的目标机器。

撤回目录条目不意味着自动删除玩家的本地安装；是否显示额外提示可以另行设计，不复用普通目录缺失来触发卸载。

## 7. 后续仓库治理材料

平台 MIT 许可证已写入根目录。对外开放贡献前，仍应补齐 `CONTRIBUTING.md`、行为准则、Issue / PR 模板和维护者职责；本文为这些材料提供内容基线，尚未创建其余正式治理文件。
