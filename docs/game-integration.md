# 游戏接入规范

| 项目 | 内容 |
| --- | --- |
| 版本 / 状态 | 0.7 / 协议草案，包含已确认产品要求及版本工程默认值；清单协议 1 已在平台实现 |
| 来源 | U-02、U-03、U-04、U-08、U-09、U-10、U-14、U-15；服务与进程细节为默认方案 |
| 适用对象 | 希望进入官方目录并由平台管理的独立游戏 |

## 1. 基本要求

游戏必须有独立启动入口，核心玩法、输入和反馈在终端内完成，不依赖额外图形窗口。菜单式游戏和实时字符游戏均可接入。

游戏可自行选择开发语言、TUI 库和渲染策略；平台不提供强制画布 API。增强终端图像协议可作为明确声明的能力，不能隐含要求所有终端支持。

每个游戏必须提供操作与退出说明、运行条件、许可证和引用说明。存档是否存在由游戏设计决定；有存档时由游戏维护格式与迁移，平台管理启动及数据存放位置。

是否联网由游戏自行设计，首版可以收录联网游戏。平台支持 Windows、macOS、Linux 是平台层面的目标；每个游戏的可用系统按其真实发布资产和清单判断。

## 2. 游戏清单

`game.json` 随安装包交付，描述解包后如何运行游戏。下面是目标协议示例，不代表已有可安装版本。

```json
{
  "manifest_version": 1,
  "id": "tank",
  "name": "坦克大战",
  "version": "0.1.0",
  "description": "守住基地，消灭敌军。",
  "authors": ["游戏维护者"],
  "launch": {
    "argv": ["./bin/tank-game"],
    "cwd": "."
  },
  "requirements": {
    "os": ["macos"],
    "arch": ["arm64"],
    "network": "none",
    "terminal": {
      "columns": 80,
      "rows": 24,
      "color": "optional",
      "unicode": "optional"
    },
    "python": {
      "version": ">=3.10",
      "modules": ["curses"],
      "packages": "requirements.txt"
    }
  },
  "data": {
    "managed_directory": true,
    "save_mode": "progress"
  },
  "documentation": {
    "readme": "README.md",
    "license": "LICENSE",
    "credits": "CREDITS.md"
  },
  "metadata": {
    "presentation": {
      "name_en": "TANK BATTLE",
      "tags": ["3 分钟", "单人"],
      "cover": {
        "background": "#1c1c1c",
        "rows": ["BB.v"],
        "cells": {"B": {"text": "▝▀", "ascii": "##", "fg": "#af875f", "bg": "#444444"}}
      }
    }
  }
}
```

（0.7）实际可运行的清单见 `games/tank/game.json` 与 `templates/minimal-game/game.json`。

### 2.1 字段约定

| 字段 | 约定 |
| --- | --- |
| `manifest_version` | 正整数，接入协议版本，与游戏版本分开 |
| `id` | 稳定唯一；必须匹配 `[a-z][a-z0-9-]{0,63}`；不能包含路径分隔符。（0.7）ID 会成为数据目录名，还须排除 Windows 保留名 `con`、`prn`、`aux`、`nul`、`com1`～`com9`、`lpt1`～`lpt9`；只允许小写也避免了大小写不敏感文件系统上的冲突 |
| `name` / `description` | 玩家可读文本，展示时不得执行其中的终端控制序列 |
| `version` | 游戏发布版本；发布后不可用不同内容覆盖同版本同平台资产 |
| `authors` | 非空作者或团队名称数组 |
| `launch.argv` | 非空字符串数组，首项为包内可执行入口，不经过 Shell 解释。（0.7）安装包的首项必须以 `./` 开头并解析到包内；开发来源（平台可执行文件所在仓库的 `games/`，或 `TUI_ARCADE_DEV_GAMES`；不从当前目录发现）可用 `{python}` 从源码运行，解释器依次取 `TUI_ARCADE_PYTHON`、`PATH` 中的 `python3`、`python`，安装包不得使用；`{dir}` 在参数中替换为游戏文件夹。首项以 `./` 开头时不得含 `{`、`}`，按原样拼接到包根目录，包根目录取清单所在目录而不跟随清单文件的符号链接，已安装来源拒绝符号链接形式的清单 |
| `launch.cwd` | 相对包根目录的工作目录，规范化后必须仍在包内 |
| `requirements.os` / `arch` | 该包真实支持的系统与架构，不代表平台已测试所有系统 |
| `requirements.network` | 草案值：`none` 无需网络、`optional` 部分功能联网、`required` 核心玩法需要网络；收录联网游戏的原则已确认 |
| `requirements.python` | （0.8）Python 游戏的运行环境：`version` 为版本要求（`>=3.10` 形式），`modules` 为必须能导入的模块，`packages` 为相对游戏目录的依赖清单文件（pip requirements 格式）。声明 `packages` 时平台为该游戏创建独立虚拟环境并安装依赖，`{python}` 解析为该环境的解释器；否则解析为满足版本要求的本机解释器。见[游戏安装规范](game-installation.md)第 4 节 |
| `requirements.terminal` | 最小列数、行数和字符 / 颜色能力需求。（0.7）能力取枚举值：`color` 为 `optional` / `16` / `256` / `truecolor`，`unicode` 为 `optional` / `required`，`keyboard` 为 `basic` / `kitty-optional`，`graphics` 为 `none` / `kitty-optional`；平台据此在大厅提示，不据此阻止启动，窗口尺寸不足时除外 |
| `data.managed_directory` | 官方托管游戏必须为 `true` |
| `data.save_mode` | 建议值：`none`、`records`、`progress`、`resume`；描述承诺能力 |
| `documentation` | 随包提供的相对路径，必须解析到包内真实文件 |
| `metadata.presentation` | （0.7）可选的画廊展示信息：`name_en`、`tags`、`cover`（最多 11 列 × 4 行，每格固定两列宽，`ascii` 为 ASCII 模式替代字符）。只是数据，不执行；格式有误时平台忽略展示信息而不拒绝游戏 |

清单字段类型、枚举和未知字段处理须在正式 Schema 中落实。无法理解的协议版本必须拒绝启动并提示平台升级，不能猜测解析。

Q-08 的工程默认方案如下，尚未生成正式 Schema：

- 平台和游戏发布版本分别采用 `MAJOR.MINOR.PATCH` 的 SemVer，不使用字符串顺序比较版本。
- `catalog_version` 与 `manifest_version` 是各自独立的正整数；首版支持集合均为 `{1}`。新平台可以同时声明支持多个旧协议，不把软件版本和协议版本混用。
- 破坏行为兼容性、新增旧平台不能忽略的必需能力时提升相应协议版本；仅添加说明性元数据可以保持协议版本不变。
- 将未来的非行为元数据放在可选的 `metadata` 对象内；未知 metadata 键可忽略，其他未知字段在正式 Schema 中按拒绝处理，防止拼错字段被静默忽略。
- 协议不兼容时禁用受影响的安装或启动并说明原因，不删除已安装程序或存档；远端目录协议不兼容不妨碍加载本地有效安装记录。
- 游戏存档版本由游戏自行维护，不能根据游戏版本或平台版本推测存档可读性。

SemVer 的公开接口与版本语义参考[语义化版本规范](https://semver.org/lang/zh-CN/)。协议兼容以明确声明和测试为准，不因为同为 `0.x` 就推定兼容。

### 2.2 包内入口与运行环境

> **（0.8）已被 U-18 取代**：游戏以源码形式从平台仓库、git 仓库或本地目录获取，任何来源都可以使用 `{python}`，运行环境由 `requirements.python` 声明并由平台准备和检查，见[游戏安装规范](game-installation.md)。下文关于预构建包与“安装包首项必须以 `./` 开头”的要求不再适用；以 `./` 开头的入口仍须位于游戏目录内。

Q-03 已确认采用预构建可运行包。安装包必须包含已准备好的入口和所需文件；支持原生可执行分发包或包含独立语言运行环境的包。Python 等解释型语言游戏须将运行环境一并打包，不能依赖玩家电脑预装相应解释器。

平台识别操作系统、CPU 架构和声明的兼容条件，自动选择对应资产。玩家的标准流程为“选择游戏 → 下载并校验 → 安装 → 启动”，不得隐含编译源码、调用系统包管理器或安装语言依赖的步骤。

不同系统可以使用不同包内入口，例如 Windows 的 `.exe`；打包工具由游戏作者和发布流程选择。构建必须针对支持矩阵验证，预构建包不代表可以忽略操作系统版本和系统库依赖。各游戏的运行环境不得互相覆盖。

首版不接收要求玩家自行准备 Python、Node 等语言环境的源码安装包，也不提供通用 `install.sh` 执行能力。公开源码和贡献者从源码运行的开发流程不受该限制。

平台不得在读取清单、展示详情或安装包校验时运行任意游戏提供的脚本。包内运行环境缺失或入口损坏时应提示修复或重装；系统版本不满足时说明不兼容原因，不自动修改玩家的系统环境。

## 3. 终端交接契约

### 3.1 启动顺序

1. 根据本地安装记录定位活动实例，验证入口仍存在。
2. 检查系统、运行环境和终端尺寸，展示网络需求；不以 GitHub 可达性推断游戏服务是否可用。
3. 确认目标游戏没有冲突中的更新、卸载等操作。
4. 暂停大厅读取输入与绘制，保存并退出大厅的终端模式。
5. 为游戏进程正确配置前台终端及信号处理，连接当前终端的标准输入、输出和错误输出。（0.7）POSIX 上游戏与平台留在同一前台进程组，无需 `tcsetpgrp`，Ctrl-C、Ctrl-Z 与窗口变化自然送达游戏。
6. 游戏独占终端运行，平台等待进程结束。
7. 在最终清理路径恢复终端模式、光标、前台所有权和大厅画面。
8. 将正常退出、启动失败、异常退出或中断分别记录和展示。

### 3.2 所有权规则

- 同一终端同一时刻只有大厅或游戏拥有交互权。
- 首版直接交接当前终端，不嵌套 PTY，不把交互输出接到 `PIPE`。
- 大厅后台目录刷新和任务状态不得在游戏画面上打印信息。
- `Ctrl+C` 应送到前台游戏，不能同时让平台无条件退出。
- 平台不提供游戏内部暂停；暂停与帮助由游戏自己实现。
- POSIX 平台需要设计前台进程组和终端属性恢复；Windows 必须提供并验证对应实现，不能留为默认后续支持。
- 游戏的网络、文件和线程资源由游戏清理；平台负责它管理的进程及终端生命周期。
- 首版不支持游戏退出后遗留脱离平台控制的后台服务。

交互退出失败时应支持受控中断和终止。具体按键应先评估与游戏按键冲突，不能仅在大厅输入循环中监听，因为游戏运行时大厅不得竞争读取输入。

（0.7）实现要点：

- **POSIX**：交接前用 termios 保存终端属性，游戏退出后以 `TCSAFLUSH`（macOS `TIOCSETAF` / Linux `TCSETSF`）恢复，同时丢弃残留按键。平台**不得**用 `SIG_IGN` 忽略 SIGINT：被忽略的信号会跨 `exec` 继承给游戏，游戏将收不到 Ctrl-C；应捕获信号（Go 的 `signal.Notify`），被捕获的信号在 `exec` 时自动恢复为默认行为。Bubble Tea 在释放终端期间忽略它收到的 SIGINT，因此平台不会随游戏一起退出。
- **兜底复位**：游戏退出后平台输出复位序列：SGR 复位、关闭鼠标上报与括号粘贴、弹出 Kitty 键盘协议（`CSI < u`）、显示光标、离开备用屏幕；然后重新读取窗口尺寸并整屏重画大厅。
- **Windows**：用 `GetConsoleMode` / `SetConsoleMode` 保存并恢复控制台输入、输出模式，同时恢复输出代码页（`SetConsoleOutputCP`）与 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`；平台用 `SetConsoleCtrlHandler` 吞掉游戏运行期间的 Ctrl-C，由游戏处理。
- **受控终止**：可采用“连续两次 Ctrl-C 且 N 秒内游戏未退出时，平台先发 SIGTERM 再发 SIGKILL（Windows 为 `TerminateProcess`）”，这不需要读取终端输入。

### 3.3 退出结果

退出码 `0` 表示进程正常完成，非零表示异常或游戏定义的运行失败；游戏胜负、得分和通关状态不得映射为平台安装或进程错误。（0.7）因 Ctrl-C 结束（被 SIGINT 终止，或退出码 130）视为玩家主动离开，不提示异常。

游戏关闭终端窗口或整个平台进程被强制终止时，不能承诺大厅仍然可见。下一次启动平台应能恢复未完成的安装管理事务。

## 4. 数据与存档契约

是否存档由游戏自行决定，平台不强制保存最高分、进度或局内状态。无存档游戏声明 `save_mode: "none"`，不需要伪造存档文件或读写接口。下面的持久化要求仅在游戏实际写入数据时适用。

平台启动时注入：

| 环境变量 | 内容 |
| --- | --- |
| `TUI_ARCADE_GAME_ID` | 经过验证的稳定游戏 ID |
| `TUI_ARCADE_DATA_DIR` | 该游戏可写的绝对数据目录 |
| `TUI_ARCADE_LOG_DIR` | 该游戏可写的绝对日志目录 |
| `TUI_ARCADE_PROTOCOL` | （0.7）平台本次遵循的接入协议版本，当前为 `1` |
| `TUI_ARCADE_LAUNCHER` | （0.7）值为 `1` 表示由平台启动，游戏可据此把“退出”显示为“返回大厅” |

（0.7）平台创建数据目录与日志目录后再交接终端；`TUI_ARCADE_DATA_DIR` 仅在 `data.managed_directory` 为 `true` 时注入。外层环境中已有的同名变量会被本次分配覆盖。平台不修改 `PYTHONPATH` 等语言相关变量。游戏把调试信息写入日志目录，不写到标准错误，以免破坏终端画面。

官方接入游戏必须将存档、用户配置和进度写入所分配的数据目录，不得写入会被替换的安装目录。无持久状态的游戏也遵守该边界，但无需伪造存档功能。

游戏在未设置这些环境变量时，必须具备独立运行的默认路径策略，并在说明中列出位置；独立运行和平台运行是否共用数据应明确说明。

### 4.1 责任分配

| 事项 | 游戏负责 | 平台负责 |
| --- | --- | --- |
| 内容结构和序列化 | 是 | 不解释内容 |
| 存档格式版本和迁移 | 是 | 展示相关说明 |
| 原子写入、损坏识别 | 是，或使用自选库 | 不把目录备份当成写入正确性的替代 |
| 专属目录创建和分配 | 遵守 | 是 |
| 卸载保留数据 | 不将数据混入安装目录 | 是 |
| 导出和备份 | 游戏可自行提供，并明确操作说明 | 是否提供统一功能及保留策略暂缓；未来若提供，仅在游戏停止后操作 |

### 4.2 兼容与失败

- 修改持久化格式时，游戏必须声明自己的存档版本和兼容策略。
- 无法读取旧存档时，不得静默重置并覆盖原文件。
- 存档写入失败必须有可见反馈，不得显示“保存成功”。
- 更新或回退游戏程序不意味着存档也已回退；迁移前备份与恢复由明确流程完成。
- 平台可以保留“旧存档可用”的提示，但不能根据目录存在就声称恢复一定成功。

当前没有选定自动备份、每游戏保留 3 份或其他平台备份策略；不得把候选方案实现为默认行为。正常卸载仍保留已有游戏数据，这与是否提供额外备份是两件事。

## 5. 游戏质量与显示要求

游戏应支持窗口变化，空间不足时暂停或明确提示，而不是持续越界写入。颜色、Unicode、特定终端扩展的需求要在清单和说明中一致。

单色和 ASCII 降级是推荐能力，不强制所有游戏提供同一字形。游戏自己的更新频率、渲染帧率和输入策略由作者决定。

### 5.1 网络行为

游戏负责自己所需的联网、账号、服务器交互与失败提示。平台展示“无需网络 / 部分功能联网 / 需要网络”，不要求游戏使用统一联机框架，也不提供默认账号体系。

本地库加载和目录缓存不能依赖游戏服务器。游戏是否降级为离线模式由其设计决定；平台不通过通用探测地址失败就阻止游戏启动，也不能承诺需要联网的游戏在断网时可玩。

## 6. 接入验收

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| GI-01 | 从包目录独立启动 | 不依赖平台内部 Python 模块或开发者路径 |
| GI-02 | 从大厅启动再退出 | 输入和绘制正常，退出后大厅可继续操作 |
| GI-03 | 缺失入口 / 不兼容协议 | 游戏不启动，提示明确，终端状态正常 |
| GI-04 | 游戏异常退出或中断 | 大厅尽可能恢复，结果不被误报为胜负 |
| GI-05 | 平台注入临时数据目录 | 游戏仅在该目录保存持久数据 |
| GI-06 | 重装程序后启动 | 玩家数据保留，是否可读取由游戏兼容规则验证 |
| GI-07 | 终端缩小再恢复 | 游戏按声明处理，退出后大厅无残留终端模式 |
| GI-08 | 依赖两个不同运行环境的游戏 | 安装任一游戏不破坏另一个游戏运行环境 |
