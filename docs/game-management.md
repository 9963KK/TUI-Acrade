# 游戏安装管理规范

> **已被取代（0.8）**：U-18 将安装模型改为从平台仓库、独立 git 仓库或本地目录获取游戏源码，由平台检查并启动，见[游戏安装规范](game-installation.md)。本文基于预构建包、GitHub 目录和 12 个名额，已不再适用，仅保留以便追溯。

| 项目 | 内容 |
| --- | --- |
| 版本 / 状态 | 0.7 / 设计草案，当前优先实现本地来源验证；0.7 补充实现建议 |
| 已确认需求 | U-05、U-06、U-10：GitHub 目录、预构建包、选择安装、最多 12 个游戏、卸载、重装和替换 |
| 默认扩展 | 更新、目录缓存、离线本地库、事务恢复、默认保留存档 |

## 1. 游戏目录与本地游戏库

远端目录描述“有哪些已发布游戏及可安装版本”，本地安装记录描述“本机实际安装了哪些游戏”。两者必须分开维护。

界面分别显示：目录游戏总数、本机兼容数、已安装数和选中待安装数。开发中的源码目录不计入可安装总数；新版本不重复增加游戏数量。

远端目录删除或暂时下架某个游戏，不得自动卸载其本地副本。已安装游戏在远端不可见时，仍根据本地记录显示详情和可用操作。

### 1.1 目录读取

- 当前本地阶段从显式配置的本地目录文件读取游戏清单，并读取本地包；界面标明本地来源。
- 下列远端读取规则在后续启用 GitHub 来源时适用，不要求当前先创建仓库。
- GitHub 模式首次进入发现页时，从固定官方 GitHub 来源读取目录。
- 公开目录和资产采用无需用户登录的流程；私有来源和账号管理不属于首版。
- 只接受校验通过的完整目录，并保留最近一次有效缓存。
- 明确展示数据更新时间；缓存不应伪装成刚刚联网获取。
- 网络异常、请求限额、无有效缓存分别展示原因和重试入口。
- 缓存过期或远端失败不阻塞本地库；需要联网的游戏仍遵循自身网络需求。
- 本地目录刷新应有节流，支持用户主动刷新，不持续轮询 GitHub。

### 1.2 目录字段

正式目录 Schema 待定义；最低应包含：

| 层级 | 信息 |
| --- | --- |
| 目录 | `catalog_version`、发布时间、游戏列表 |
| 游戏 | 稳定 ID、名称、简介、作者、分类、最新稳定版本、说明和来源 |
| 版本 | 游戏版本、兼容接入协议、变更说明 |
| 安装包 | 系统、CPU 架构、运行条件、文件大小、SHA-256、固定下载地址 |

版本字段用于展示和选择；目录需明确标记最新稳定版本，不能按字符串排序猜测“最新”。

目录元数据与随包清单的 ID、版本、平台和协议必须一致。安装任务一旦创建，就固定目录快照中的版本、资产标识和校验值，刷新目录不能改变已经排队的任务。

SHA-256 用于检测内容不一致，不替代来源审核。当前只从明确配置的本地开发来源读取目录和包；对外发行时固定为受维护者控制的 GitHub 目录与发布资产，暂不开放任意 URL 安装。

本地来源同样经过清单、校验值、解包边界、名额和安装事务检查，不能因为不联网就绕过管理规则。本地文件路径由本地来源适配器解析，不把开发者路径写入未来的公开目录。相同安装计划分别通过本地与远端来源获取包后，应进入同一校验和提交流程。

## 2. 发现与选择界面

首次启动进入空游戏库时，展示“发现并安装游戏”入口。以后启动优先加载本地游戏库，不必等待网络。

发现页应提供搜索、兼容性筛选、游戏详情和多选安装。详情包含玩法、操作、作者、许可证、引用来源、版本说明、下载大小、网络需求和运行要求。联网与否不作为拒绝收录的条件，按游戏自身设计声明。

选择后展示计划中的动作、总下载大小和安装后名额。用户在确认安装计划前不会发生下载、移除或程序执行。

```text
发现游戏                         已安装 8 / 12

搜索：________________     筛选：本机可安装

选择  游戏名称       最新版本   本地状态
[✓]   坦克大战       0.2.0      待安装
[ ]   贪吃蛇         1.1.0      已安装
[ ]   推箱子         0.3.0      可更新
[ ]   地牢探险       0.1.0      本机暂不支持

已选 1 个，安装后 9 / 12
预计下载：……

空格 选择    Enter 详情    I 安装所选    Esc 返回
```

示例游戏和数字仅用于说明。已安装游戏通过详情页执行更新或重装，不因再次选中而占第二个名额。不兼容项目可查看说明，不可选择安装。

## 3. 12 个名额

上限作用于同一用户、同一本地游戏库中已登记的不同 `game_id`。首版不提供多个用户档案或多个游戏库绕过该限制。

| 情况 | 名额处理 |
| --- | --- |
| 新安装 | 计划时预留 1 个，提交成功后转为已安装 |
| 更新 / 重装同一游戏 | 占原有名额，不重复预留 |
| 卸载 | 提交卸载后释放名额，残留程序清理可稍后重试 |
| B 替换 A | 锁定 A 的名额，提交时 A → B，总数不变 |
| 下载失败 / 提交前取消 | 释放该任务预留，不增加安装数 |
| 存档、日志、缓存、旧程序备份 | 不占额外名额 |
| 已登记但文件损坏的游戏 | 仍占原名额，提供修复或卸载入口 |

常规安装应维持 `已安装数 + 新安装预留数 <= 12`。替换任务绑定一个独占的旧游戏名额；两个任务不能同时把 A 作为替换目标。

名额检查必须在持有安装记录修改锁时进行，而非仅在 UI 勾选时判断。满额时允许更新、重装和替换，禁止无替换目标的第 13 个新安装。

（0.7）提交时持锁按 `installed.json` 的实际条目数加本进程内的预留计算即可；预留只在平台进程内存中维护，无需单独持久化：进程中断即意味着预留失效。另一平台实例的预留由全局锁与提交时的复核保证不会超额。大厅画廊每页 6 格，12 个名额正好两页；空展位可作为“发现游戏”的入口。

## 4. 操作语义

| 操作 | 输入 | 成功结果 | 存档默认行为 |
| --- | --- | --- | --- |
| 安装 | 未安装 ID、选定版本 | 新增活动安装实例 | 使用该 ID 的独立数据目录 |
| 更新 | 已安装 ID、新版本 | 同一 ID 切换至新版 | 保留，游戏负责迁移 |
| 重装 | 已安装 ID、当前版本 | 重新获取同版本并替换程序 | 保留 |
| 替换 | 已安装 A、未安装 B | 移除 A 的活动记录，激活 B | A 保留，B 使用自己的数据 |
| 卸载 | 已安装 ID | 移除活动记录及程序 | 保留 |
| 删除数据 | 明确选择的游戏数据 | 删除对应存档、进度和设置 | 必须单独明确选择 |

替换不能把 A 的存档当作 B 的存档。B 原来遗留的数据可以继续使用，但能否兼容仍由 B 判断。

重装默认固定为当前版本；远端资产不存在时应提示，不得静默升级。若 B 已安装，不提供“A 替换成 B”造成名额或数据歧义的操作，应分别引导管理 A 和 B。

普通卸载的操作摘要明确提示保留已有游戏数据。有存档时包括存档；无存档游戏不应显示误导性的“已备份存档”。存在数据目录时可以提供默认关闭的“同时删除数据”选项；用户明确选择并执行后，无须增加重复确认流程。

## 5. 安装任务状态机

安装状态属于任务，不应覆盖已有安装的可用状态。旧版本保持有效，直到新实例被提交为活动版本。

```text
queued → preflight → downloading → verifying → staging → ready
                                                        ↓
                                                   committing
                                                        ↓
                                                   committed
                                                        ↓
                                                    cleanup
                                                        ↓
                                                   completed
```

- `committing` 之前可失败或取消：保留旧实例，释放预留，清理暂存。
- `committing` 期间不立即响应取消，应先完成或恢复提交，再报告实际状态。
- `committed` 之后旧程序清理失败：新状态仍有效，记录“待清理”，不能误报为安装整体失败。
- 游戏第一次运行后发生的存档迁移，不在安装事务的自动回滚范围内。

### 5.1 准备与校验

1. 检查名额、操作冲突、目标兼容性、磁盘空间和来源。
2. 下载到临时位置，支持超时、取消和明确重试。
3. 校验预期大小和 SHA-256；不一致时禁止解包激活。
4. 解包时拒绝绝对路径、越界路径和越界链接，限制不合理的解压体积。
5. 检查包内清单、文档、入口及运行条件；静态检查不得执行任意安装脚本。
6. 在与程序目录同一文件系统中准备独立实例，进入 `ready`。

磁盘空间检查要考虑临时包、新程序和旧程序同时存在，不只看下载大小。运行自检若需要执行游戏代码，应是明确约定的扩展，不是静态校验的隐含步骤。

（0.7）包格式与解包：

- POSIX 目标使用 `tar.gz`，保留可执行权限。Python `tarfile` 的 `filter="data"`（3.12 起提供，并回移至 3.10.12 / 3.11.4）可拒绝绝对路径、越界路径与越界链接；Go / Rust 须自行校验每个条目规范化后的路径与链接目标。
- Windows 目标使用 `zip`。`zipfile` 不还原 Unix 权限位，因此 zip 不用于 POSIX 目标。
- 解包前按目录声明的大小校验下载文件，解包中限制总解压体积与文件数量，防御压缩炸弹；超限即中止并清理暂存。
- Python 游戏打包建议使用 PyInstaller 的 `onedir` 模式：`onefile` 每次启动都要解压到临时目录，启动慢，也更容易被 Windows Defender 误报。
- 平台自己下载并解包的文件在 macOS 上不带隔离属性，不受 Gatekeeper 首次打开拦截；但 arm64 程序至少需要 ad-hoc 签名，打包后修改二进制会使签名失效。

### 5.2 提交与恢复

推荐以安装记录作为活动实例的唯一事实来源。提交顺序：

1. 持有修改锁，写入包含旧状态、新状态、实例路径和阶段的事务记录。
2. 确认新实例准备完整且路径可访问。
3. 可靠地替换安装记录，切换活动实例；替换 A → B 必须在同一次记录提交中完成。
4. 标记已提交，释放名额预留，旧实例进入待清理集合。
5. 清理不再被安装记录引用的实例，完成任务记录。

实际文件写入需要考虑刷新、原子替换和目录持久化；不能只调用一次重命名就声称跨多个文件更新绝对原子。

启动恢复必须按事务记录和安装记录共同判断：

| 中断位置 | 恢复行为 |
| --- | --- |
| 下载或校验中 | 保留旧状态；清理或重新下载临时包 |
| 新实例已准备但安装记录未切换 | 旧实例仍活动；允许清理新实例 |
| 安装记录已切换但事务标记未更新 | 识别新实例已活动，继续提交后的清理 |
| 已提交、旧程序未清理 | 保持新状态，重试清理；不恢复旧游戏名额 |
| 安装记录或事务记录损坏 | 保留现有文件与备份，报告恢复问题，不猜测后批量删除 |

同一游戏运行与修改须共享协调机制，避免“检查未运行后立即被另一入口启动”的竞态。首版通过平台全局管理锁及运行登记串行协调。

（0.7）推荐实现：**单一事实来源 + 启动时回收**。

- 激活只有一步原子操作：写临时文件 → `fsync` → `os.replace` 替换 `installed.json`，使其指向新的实例目录；替换前把上一份有效记录保留为 `installed.json.bak`。Windows 上目标文件被杀毒软件等短暂占用时 `replace` 会失败，需有限次重试。
- 平台启动时持锁回收：删除未被 `installed.json` 引用的实例目录与残留的暂存、临时下载。上表中“新实例已准备但记录未切换”“记录已切换但事务标记未更新”“已提交、旧程序未清理”三种情况由此自动收敛，不需要逐阶段的事务日志；`transactions/` 只用于断点续传等体验功能。
- `installed.json` 与 `.bak` 都无法解析时，按上表最后一行处理：保留文件并报告，不做回收删除。
- 全局锁必须跨进程并在进程崩溃时自动释放：POSIX 用 `flock`，Windows 用 `LockFileEx`。不使用“写 PID 文件”的方式，以免崩溃后留下陈旧锁。玩家可能在两个终端窗口同时打开平台。
- 运行登记可用“运行中持有该游戏的共享锁、修改时申请排他锁”实现，平台进程退出时锁随之释放。

## 6. 批量与异常行为

- 批量任务逐个反馈成功、失败和取消；失败一个游戏不撤销其他已成功游戏。
- 安装计划确认时固定预留名额，失败或取消后及时释放。
- 重复点击不得产生同一游戏的重复事务；给出已有任务状态。
- 网络重试不得重新执行已提交的安装或卸载动作。
- 卸载清理失败时说明残留文件，提供重试；不得波及游戏数据目录。
- 删除游戏数据不得与运行中的游戏、存档备份或数据恢复并发。
- Q-07 尚未选定平台统一备份，不默认启用自动快照或固定保留份数。未来若提供该可选能力，只在游戏停止后复制完整数据目录。
- 游戏下架、目录刷新失败和安装包不存在都是不同状态，提示应区分。

## 7. 发布约定

本节为后续 GitHub 发行约定；当前只做本地，仓库地址与发布权限暂缓确定。

每个游戏的版本安装包通过 GitHub Releases 发布；目录集中列出可安装资产。先上传并验证所有声明兼容的资产，再发布引用这些资产的目录，避免目录先可见而文件尚未就绪。

安装资产必须是预构建可运行包，构建和语言运行环境准备由贡献者与发布流程完成。平台自动匹配目标系统资产，玩家无需自行挑选文件名；没有兼容资产时标为不可安装，不回退到本地源码编译。

同一个游戏版本和平台资产不应以不同内容重发。修复应发布新版本；安装记录保留来源、版本和校验值以便复现问题。

公开资产可匿名下载。GitHub REST API 存在请求限额，因此实现需要缓存和节流，而不是强制普通用户提供 Token。

（0.7）建议完全绕开 REST API：目录文件本身作为固定地址的 Release 资产或仓库原始文件发布，目录中为每个安装包写明固定下载地址 `https://github.com/<owner>/<repo>/releases/download/<tag>/<file>`。这类下载不计入 REST API 限额，上文的节流与限额处理可以大幅简化。SHA-256 只保证安装包与目录一致，不能防止目录本身被篡改；公开发行后可考虑对目录文件签名（如 minisign），平台内置公钥校验。打包的 Python 运行环境可能找不到系统 CA 证书，HTTPS 下载须随包提供 `certifi` 或使用系统证书库（如 `truststore`）；Go / Rust 可直接使用系统证书库。

## 8. 验收矩阵

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| GM-01 | 首次联网、无本地游戏 | 展示目录、兼容性，可选择安装 |
| GM-02 | 已装 11 个，批量选择 2 个新游戏 | 不能创建超额计划，提示只剩 1 个名额 |
| GM-03 | 已装 12 个，更新或重装其中一个 | 允许操作，安装数保持 12 |
| GM-04 | 已装 12 个，以 B 替换 A 成功 | 记录中 A 被 B 替代，总数保持 12 |
| GM-05 | B 下载失败、校验失败或准备阶段取消 | A 仍可启动，名额和 A 数据不变 |
| GM-06 | 替换提交前后分别强制中断平台 | 恢复后 A 或 B 有一个活动记录，不同时占两个名额 |
| GM-07 | 重装当前版本但资产已删除 | 明确失败，当前安装保留，不自动变更版本 |
| GM-08 | 普通卸载后重新安装 | 原有存档保留，游戏按兼容策略处理 |
| GM-09 | 用户明确选择同时删除数据 | 仅删除目标游戏的数据，不影响其他游戏 |
| GM-10 | 无网络、目录限流、目录内容损坏 | 本地库可加载，最近有效缓存不被坏数据覆盖 |
| GM-11 | 游戏从远端目录消失 | 本地副本不被自动卸载 |
| GM-12 | 两个任务争抢最后一个名额或同一替换目标 | 仅一个任务获得预留或目标锁 |
| GM-13 | 更新正在运行的游戏 | 排队或提示退出，不替换正在执行的程序 |
| GM-14 | 包含越界解压路径或校验值不符的包 | 拒绝激活，不修改安装目录外的文件 |
| GM-15 | 新安装已提交但清理旧程序失败 | 新安装有效，清理可重试，不回滚存档 |
| GM-16 | 批量安装部分成功、部分失败 | 保留成功项，失败项可单独重试 |
| GM-17 | 目录中同时存在离线、部分联网和联网游戏 | 正确展示需求，允许安装兼容项目，不因联网属性排除 |
| GM-18 | 同一游戏提供多个系统 / 架构的安装包 | 自动选择兼容资产；无匹配项时提示，不能安装错误资产或转为源码构建 |
| GM-19 | 无 GitHub 仓库配置，仅有本地目录和包 | 可验证发现、选择安装与完整管理流程，清楚显示本地来源 |
